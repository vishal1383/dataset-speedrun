# Initial experiments

I ran four dataset recipes with two initialization seeds on two DGX Sparks.
All eight runs completed. Each run used 400 updates and 3,276,800 target tokens.
The model, tokenizer, optimizer, schedule, and evaluation sets remained fixed.

## Result

The full candidate pool gave the lowest final loss on both evaluation splits.
The random-quarter recipe increased mean audit loss from 3.0192 to 3.1702 nats/token.
The diversity and length-stratified subsets did not recover that loss.

All recipes reached the registered development target of 3.5 nats/token at the update-150 evaluation.
The result therefore shows **no measured update reduction at this target**.
The smaller subsets compressed data storage, but they did not preserve final model quality at the fixed training budget.

| Recipe | Dev loss, mean ± sample SD | Audit loss, mean ± sample SD |
|---|---:|---:|
| Full pool | 2.6656 ± 0.0060 | 3.0192 ± 0.0047 |
| Random quarter | 2.7840 ± 0.0002 | 3.1702 ± 0.0080 |
| Token-diverse quarter | 2.9079 ± 0.0077 | 3.1735 ± 0.0122 |
| Length-stratified quarter | 2.8130 ± 0.0080 | 3.1742 ± 0.0095 |

The primary artifact is the per-run `result.json`, including all development evaluations.
`summary.csv`, `TABLE.md`, and `loss_curves.png` are generated by `report.py`.

## Interpretation

My assessment is that repeated exposure to a small subset loses useful distribution coverage in this setup.
The subset runs process the same token budget as the full-pool runs, with more repeated samples.
This mechanism is consistent with the observed loss gap, but the current experiments do not isolate its cause.

The token-diversity score selects longer documents and changes the training distribution.
Its weaker development result argues against using lexical diversity alone as a quality score here.
Its audit loss is close to the other quarter-sized recipes.

The development loss is lower than audit loss across all recipes.
The development and audit streams use different contiguous portions of the source validation split.
Their sizes differ. This release does not establish the cause of the split-level loss difference.
Compare recipes within each split rather than comparing the absolute loss values between splits.

## Compute and limits

Each run used one NVIDIA GB10. The container was `nvcr.io/nvidia/pytorch:26.03-py3`.
Train-loop time averaged about 12.4 seconds per run. Timing varied between the two hosts.
These times describe this small model and workload; they are not NanoGPT leaderboard times.
The complete preparation took about 8.9 seconds, including source download and tokenization.
Selecting all four document lists took about 0.13 seconds on the CPU.
The preparation time excludes container startup. No teacher model or dataset search was used.

Two seeds, one small synthetic-story corpus, and one model size provide initial evidence only.
The 3.5-nat target is too coarse to separate these methods at the registered evaluation interval.
The data pool is a deterministic source prefix, not a representative sample of the entire TinyStories dataset.
Exact document deduplication does not exclude near duplicates or template overlap.
The audit set is public after release and must not serve as an untouched test for future tuning.

## Next experiment

The next useful comparison is a teacher-scored subset against the random-quarter control at matched token storage.
A useful score should target predictable structure that the small model has not learned.
The construction cost must include teacher inference.
A separate bounded-gradient track remains future work; this release contains no gradient-distillation experiment.
